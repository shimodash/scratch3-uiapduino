# キーボードブロック 実装仕様

scratch3-uiapduino のキーボード対応の実装仕様。**実装済みの内容を書いてある。**

このファイルは当初、マウス（段階 1）の完了時点で「これから作るもの」として書いた。
実装の過程で設計が変わった箇所があるため、実物に合わせて書き直してある。
何がどう変わったかは末尾の「修正履歴」を見ること。

---

## 0. 前提

| | 状態 |
|---|---|
| マウスのブロック | **全ブロック実機確認済み** |
| キーボードのブロック | **全ブロック実機確認済み**（2026-08-07） |
| プロトコル | **バージョン 5** |
| USB 設定 | `Keyboard+Mouse+WebHID`（`usb=kbdweb`）。取り違えはコンパイル時に停止する |

### ⚠ 基板の書き込み直しが必要

キーボードのブロックを入れるにあたって `.ino` を変えたので、
`PROTOCOL_VERSION` を **3 → 5** に上げてある。
古いスケッチのままだと接続時のバージョン照合で弾かれる
（開発者コンソールに `デバイス=4 / この拡張機能=5` のように出る）。

理由は「[6. `Keyboard.write()` を使ってはいけない](#6-keyboardwrite-を使ってはいけない)」に書いた。

## 1. 設計方針：押しっぱなしは囲みブロックの内側にだけ作れる

マウスで採った方針をキーボードにも適用する。

**`キーを押したままにする` / `キーを離す` を単独のブロックとしては置かない。**

利用者が「離す」を書き忘れれば、Shift や Ctrl が押されたまま残る。
そこで USB を抜かれると、操作していたアプリに修飾キーが押されたままの状態が取り残される。

修飾キーの押しっぱなしは、マウスのボタンより厄介だ。ボタンなら
「どこかを 1 回クリックすれば消える」のに対し、修飾キーは気づきにくく、
**その後のすべてのキー入力が化ける。**

そこでマウスの `ドラッグしながら〔 〕` と同じく、押しっぱなしを
**囲みブロックの内側にだけ**作れるようにした。囲みを抜ければ必ず離れる。

デバイス側の `KEY_PRESS`（`0x32`）/ `KEY_RELEASE`（`0x33`）は、この囲みブロックが
中身の前後で使う。**ブロックとして露出はしない。**
`KEY_RELEASE_ALL`（`0x34`）は `PANIC` の経路で使う。

### ⚠ 「ショートカット」という概念は持たない

当初は `キーボードの [Ctrl▼] を押しながら [c] キーを押す` という 1 コマンドのブロックを作り、
デバイス側に `KEY_SHORTCUT`（`0x35`）を置いていた。**どちらも消した。**

**キーボードに「ショートカットキー」というキーは存在しない。**
あるのは「キーを押す」と「修飾キーを押したままにする」の 2 つだけで、
その組み合わせを表すのが囲みブロックである。
専用のコマンドを別に持つと、同じことを 2 通りで表せる状態になる。

`0x35` は空き番として残してある（デバイスは `rsp_err` を返す）。

## 2. ブロック

| ブロック（日本語） | 形 | コマンド |
|---|---|---|
| `キーボードで [Hello UIAPduino] と打つ` | COMMAND | `KEY_TEXT`（`0x30`）を 29 文字ずつに分けて連投 |
| `[Enter▼] キーを押して離す` | COMMAND | `KEY_WRITE`（`0x31`） |
| `キーボードの [Ctrl▼] を押しながら〔 〕` | **LOOP（囲み）** | `KEY_PRESS`（`0x32`）/ `KEY_RELEASE`（`0x33`） |

既存の `キーとマウスをすべて離す`（`PANIC`）はそのまま。

パレットではキーボードをマウスより**前**に置く。

`Ctrl + C` は次のように書く。

```
キーボードの [Ctrl▼] を押しながら〔
    キーボードで [c] と打つ
〕
```

入れ子にできる。`キーボードの [Ctrl▼] を押しながら〔 キーボードの [Shift▼] を押しながら〔 … 〕 〕` で
`Ctrl + Shift + …` になる。

### 文言（`message` 定数）

```js
keyType: {
    ja: 'キーボードで [TEXT] と打つ',
    'ja-Hira': 'キーボードで [TEXT] とうつ',
    en: 'type [TEXT] on the keyboard'
},
keyWrite: {
    ja: 'キーボードの [KEY] キーを押して離す',
    'ja-Hira': 'キーボードの [KEY] キーをおしてはなす',
    en: 'press and release [KEY] on the keyboard'
},
keyModifierWhile: {
    ja: 'キーボードの [MOD] を押しながら',
    'ja-Hira': 'キーボードの [MOD] をおしながら',
    en: 'hold [MOD] on the keyboard while'
}
```

メニュー項目の文言（`Enter` `Backspace` などのキー名、`Ctrl` `Shift` などの修飾キー名）は
**英字のまま。** キートップの刻印と一致する方が分かりやすい。

### ⚠ 「キーボードで」「マウスの」を頭に付けている

**`[ ] と言う` と取り違えられないため。** 動く先は Scratch の中ではなく PC 本体である。

`とタイプする` では**どこに**打たれるのかを言っていない。子どもは
「Scratch の中の何かに打つ」と読む。道具の名前を出せば、そこが確定する。

アイコンも同じ理由で、基板ではなく**キーボードとマウスの絵**にしてある
（`keyboardIconURI` / `mouseIconURI`）。基板の絵だと「UIAPduino に何かする」に読めて、
狙いと逆に働く。絵は目を引くだけで読み上げると消えるので、文言と両方で言う。

マウスのブロックも同様に `マウスの [左▼] ボタンをクリックする` のように直してある。
`マウスを 右へ [ ] 下へ [ ] 動かす` は元から名指ししていたのでそのまま。

## 3. ワイヤフォーマット

### `KEY_TEXT` (`0x30`) — 文字列をタイプする

| バイト | 内容 |
|---|---|
| `[0]` | `0x30` |
| `[1]` | フラグ（`0x80` = 続きあり）|
| `[2..30]` | ASCII、0 終端 |

#### ⚠ 1 回に送れるのは **29 文字**

Feature Report は 32 バイトだが、**デバイス側が `buf[31] = 0` で終端を強制する。**

```c
case CMD_KEY_TEXT:
  buf[31] = 0;                              // ← ここで 30 文字目が潰れる
  for (uint8_t *p = &buf[2]; *p; p++) keyTap(*p);
```

したがって文字を置けるのは `[2..30]` の **29 バイト**。30 文字入れると
最後の 1 文字が消える。**気づきにくい壊れ方なので注意すること。**

Scratch 側は `KEY_TEXT_CHUNK = 29` で切って連投する。片方だけ変えないこと。

#### ⚠ フラグはデバイス側が見ていない

`[1]` のフラグは読まれていない。**29 文字ずつに切って順に送れば、そのまま順番にタイプされる。**
`uiapduinoProcessor` のキューが直列化するので、順序は保証される。

Scratch 側は最後以外のコマンドで `0x80` を立てている。将来デバイス側が
見るようになったときのためで、**「立てないと繋がらない」わけではない。**

#### 応答待ち時間

`keyTap()` は 1 文字あたり 40ms かかる（後述）。29 文字で約 1.2 秒。
既定の 3 秒では余裕が乏しいので、Scratch 側は文字数から見積もる。

```js
_typeTimeout (length) {
    return 1000 + (length * 80);
}
```

#### ⚠ ASCII のみ。日本語は打てない

デバイスは HID のキーコードを送るだけで、**IME は通らない。**
知らないバイトは `Keyboard.cpp` の `_toHID()` が `false` を返して黙って捨てる。

Scratch 側は印字可能な ASCII（`0x20`〜`0x7E`）以外を送らず、
**開発者コンソールに警告を出す。** 無言で化けるのが最悪なため。

#### ⚠ US 配列前提

HID はキーコードを送るだけなので、**PC 側のキーボード配列で解釈が変わる。**
日本語配列（JIS）の PC では `@ : _ [ ] \ ^` などがずれる。

英数字とスペースは配列によらず正しく入る。**まずはそこまでを確実に動かし、
記号の配列対応は後回しでよい。** 対応する場合は、ブロックに
`キーボードの配列 [US▼/JIS▼]` を持たせ、Scratch 側（JS）で記号のキーコードを
差し替える表を持つことになる。デバイス側は変更不要。

### `KEY_WRITE` (`0x31`) — キーを押して離す

| バイト | 内容 |
|---|---|
| `[0]` | `0x31` |
| `[1]` | キーコード |

デバイス側は `keyTap()` を呼ぶ。

### `KEY_PRESS` (`0x32`) / `KEY_RELEASE` (`0x33`) — 押したままにする / 離す

| バイト | 内容 |
|---|---|
| `[0]` | `0x32` または `0x33` |
| `[1]` | キーコード（修飾キーなら `0x80`〜`0x83`）|

`キーボードの [Ctrl▼] を押しながら〔 〕` が中身の前後で使う。**ブロックとしては露出しない。**

`KEY_PRESS` はデバイス側の `keyHeld` を立てる。これで
**最後のコマンドから 5 秒の見張り**が効くようになり、
囲みの途中でスクリプトが止まっても最後は必ず離れる。

## 4. キーコード表

`arduino_core_ch32` の `Keyboard.h` の定数。

### `KEY_WRITE` のメニュー（29 項目）

| キー | 値 | キー | 値 |
|---|---|---|---|
| Enter | `0xB0` | Home | `0xD2` |
| Esc | `0xB1` | PageUp | `0xD3` |
| Backspace | `0xB2` | Delete | `0xD4` |
| Tab | `0xB3` | End | `0xD5` |
| Insert | `0xD1` | PageDown | `0xD6` |
| → | `0xD7` | ← | `0xD8` |
| ↓ | `0xD9` | ↑ | `0xDA` |
| CapsLock | `0xC1` | PrintScreen | `0xCE` |
| F1–F12 | `0xC2`–`0xCD` | NumLock | `0xDB` |

修飾キー単体はこのメニューに**出さない。** 単体で押しても意味がなく、
押しっぱなしを作る道具にしかならない。

### `キーボードの [MOD▼] を押しながら` のメニュー

| 表示 | 値 | `Keyboard.h` |
|---|---|---|
| Ctrl | `0x80` | `KEY_LEFT_CTRL` |
| Shift | `0x81` | `KEY_LEFT_SHIFT` |
| Alt | `0x82` | `KEY_LEFT_ALT` |
| Windows | `0x83` | `KEY_LEFT_GUI` |

そのまま `KEY_PRESS` / `KEY_RELEASE` のキーコードとして渡す。

メニューは `acceptReporters` なので何でも渡ってくる。範囲外の値が来たら
**Ctrl に丸める。** そのまま流すと、押したまま離せない別のキーを掴みかねない。

## 5. 囲みブロックの作り

マウスの `ドラッグしながら〔 〕` と同じ `BlockType.LOOP`。
「中身が終わったらもう一度呼ばれる」という性質を使う。

```
1 回目の呼び出し : KEY_PRESS → util.startBranch(1, true) → 中身が動く
2 回目の呼び出し : KEY_RELEASE。startBranch を呼ばないのでここで終わる
```

`util.startBranch()` は同期的に呼ばなければならないので、`KEY_PRESS` の応答は待たない。
待たなくても順序は崩れない。processor のキューが直列化するので、
中身の `と打つ` は必ず `KEY_PRESS` の後ろに並ぶ。

### 押したキーはスタックフレームに覚える

メニューは `acceptReporters` なので、2 回目の呼び出しで別の値が返ってくることがある。
`util.stackFrame` に押したキーコードを入れておき、**それを離す。**

### 入れ子はキーごとに数える

マウスは 1 つしかないので `_dragDepth` という単一の深さで足りたが、
修飾キーは `Ctrl` と `Shift` を同時に押せる。そこで
`Map<キーコード, 数>` を持ち、**押すのは 0 → 1 のときだけ、
離すのは 1 → 0 のときだけ**にする。

これで次の両方が成立する。

- `Ctrl` の中に `Shift` → 両方押される。内側を抜けても `Ctrl` は残る
- 同じ修飾キーの二重の入れ子 → 押すのも離すのも 1 回ずつ

### `_inputHeld` は数え直す

`_inputHeld` は USB を抜かれたときに後始末が要るかの判断に使う。
ドラッグと修飾キーは同時に成立しうる（ドラッグの囲みの中に修飾キーの囲みを置ける）ので、
片方を離しただけで倒してはいけない。

```js
_updateInputHeld () {
    this._inputHeld = this._dragDepth > 0 || this._modifierCounts.size > 0;
}
```

`mouseDragWhile` もこれを呼ぶように直してある。

## 6. `Keyboard.write()` を使ってはいけない

**これが `PROTOCOL_VERSION` を上げた理由。**

`arduino_core_ch32` の `Keyboard.write()` は次のようになっている。

```cpp
size_t KeyboardClass::write(uint8_t key) {
    ...
    _modifier = modBit;      // ← 押しっぱなしにした Ctrl がここで消える
    memset(_keys, 0, 6);
    _keys[0] = hid;
    _sendReport();
    delay(20);
    releaseAll();            // ← ここで全部離れる
    delay(20);
```

レポート全体を組み立て直すので、`KEY_PRESS` で押したままにしてある `Ctrl` が
**消えたうえに、最後の `releaseAll()` で全部離れる。**
`Keyboard.print()` は内部で `write()` を呼ぶので同じ。

そのままだと `キーボードの [Ctrl] を押しながら〔 キーボードで [c] と打つ 〕` が
**無言で修飾キー無しになる。** 一番わかりにくい壊れ方である。

そこでスケッチ側に `keyTap()` を置いた。

```c
static void keyTap(uint8_t k) {
  uint8_t base;
  bool charShift = needsShift(k, &base);
  bool useShift  = shiftHeld ? !charShift : charShift;

  // この 1 文字のために Shift の状態を合わせる
  if (useShift != shiftHeld) {
    if (useShift) Keyboard.press(KEY_LEFT_SHIFT);
    else          Keyboard.release(KEY_LEFT_SHIFT);
  }

  Keyboard.press(base);
  delay(20);
  Keyboard.release(base);

  // 押しっぱなしの状態へ戻す
  if (useShift != shiftHeld) {
    if (shiftHeld) Keyboard.press(KEY_LEFT_SHIFT);
    else           Keyboard.release(KEY_LEFT_SHIFT);
  }
  delay(20);
}
```

`press()` / `release()` は該当のキーだけを足し引きするので、
**外側で押している修飾キーがそのまま残る。**

`needsShift()` と `shiftHeld` はバージョン 5 で足した。理由は次の 2 節にある。

`CMD_KEY_TEXT` と `CMD_KEY_WRITE` の両方をこれに切り替えた。
ライブラリは変更していない（変更すると利用者が改造版のコアを要求される）。

### 待ちは 20ms ずつ。短くしない

どちらも USB のポーリング（10ms）に確実に拾わせるためのもの。
`press` 側を 10ms に縮めると `"ll"` `">>>"` のような連続する同一文字で
1 文字欠ける（`Keyboard.cpp` のコメント）。1 文字あたり 40ms かかる。

### ⚠ ただし `press()` に大文字を渡してもいけない

**バージョン 4 の不具合。バージョン 5 で直した。**

```cpp
size_t KeyboardClass::press(uint8_t key) {
    if (!_toHID(key, &hid, &modBit)) return 0;
    if (modBit) {
        _modifier |= modBit;
        _sendReport();
        return 1;              // ← ここで返る。hid が _keys[] に入らない
    }
    for (int i = 0; i < 6; i++) { ... }
}
```

`'H'` は `_toHID()` が **Shift ビットとキーコードの両方**を返すのに、
`press()` は `modBit` があるとそこで返ってしまい、**キーを押さない。**
Shift を押しただけで終わるので、`Hello` とタイプすると `ello` になる。

`write()` は `_modifier` と `_keys[0]` の両方を組み立てるので問題にならなかった。
`press()` へ切り替えたときにこの違いを踏んだ。

対処として `needsShift()` を置き、**文字を「刻印どおりに押せるキー」と
「Shift が要るか」に分解**してから、Shift は `keyTap()` が自分で押す。

```c
static bool needsShift(uint8_t k, uint8_t *base) {
  if (k >= 'A' && k <= 'Z') { *base = k - 'A' + 'a'; return true; }
  static const char shifted[] = "!@#$%^&*()_+{}|:\"~<>?";
  static const char plain[]   = "1234567890-=[]\\;'`,./";
  ...
}
```

表は `Keyboard.cpp` の `_toHID()` と同じ組み合わせ。**片方だけ変えないこと。**

実際のキーボードに `H` というキーは無く、あるのは `h` のキーと Shift である、
という当たり前の形に戻したことになる。

### 押しっぱなしの Shift は大文字小文字を反転させる

| 書いたもの | 打たれるもの |
|---|---|
| `キーボードで [Hello] と打つ` | `Hello` |
| `キーボードの [Shift▼] を押しながら〔 キーボードで [Hello] と打つ 〕` | `hELLO` |
| `キーボードの [Shift▼] を押しながら〔 キーボードで [1] と打つ 〕` | `!` |

大文字を打つのに内部で Shift を使う以上、外側の Shift と重なったときの
振る舞いを決めておかないと、どちらが勝つのか説明できない。
反転なら「Shift を押しながらタイプすると大文字小文字が入れ替わる」の一文で済む。

デバイス側は `KEY_PRESS` で Shift を押されたことを `shiftHeld` で覚えておき、
`keyTap()` が文字ごとの要否と突き合わせる。

```c
bool charShift = needsShift(k, &base);
bool useShift  = shiftHeld ? !charShift : charShift;
```

Shift の状態がその 1 文字のために変わる場合は、押す前に合わせて、離した後に戻す。

`Ctrl` / `Alt` / `Windows` は反転に関わらない。したがって
`キーボードの [Ctrl▼] を押しながら〔 キーボードで [C] と打つ 〕` は `Ctrl + Shift + c` になる。
**`Ctrl` と組み合わせる文字は小文字で書くこと。**

## 8. 実機で確認すること

**下記はすべて確認済み（2026-08-07、プロトコル 5）。**
作り直したときの再確認用に残してある。

**メモ帳で確認すること。** 「Scratch の上で試す」と、Scratch 自身が入力を
受け取るだけの状況になり、何も一般化できない。

1. 基板を書き込み直してから接続し、バージョン照合が通る
2. `キーボードで [Hello UIAPduino] と打つ` が**大文字も欠けずに**入力される
3. 記号が打てる（`!@#$%^&*()_+{}|:"~<>?` と `-=[]\;'` `` ` `` `,./`）
4. **29 文字を超える文字列**が、途切れず・重複せず・順番どおりに入る
   （境界の 29 / 30 / 31 文字を試す）
5. `[Enter▼] キーを押して離す` で改行される。矢印・Backspace・Delete も効く
6. `キーボードの [Shift▼] を押しながら〔 キーボードで [Hello] と打つ 〕` で `hELLO` になる
7. `キーボードの [Ctrl▼] を押しながら〔 キーボードで [c] と打つ 〕` でコピーができる
   （`キーボードの [Ctrl▼] を押しながら〔 キーボードで [v] と打つ 〕` で貼れる）
8. **囲みを抜けた後、修飾キーが残っていない**（続けて文字をタイプして化けないこと）
9. 入れ子（`Ctrl` の中に `Shift`）で `Ctrl + Shift + …` になる
10. 囲みの中身が動いている最中に停止ボタンを押すと、修飾キーが離れる
11. 囲みの中で `このスクリプトを止める` を使っても、5 秒後に離れる
12. 日本語や絵文字を渡したときに、無言で化けず警告が出る

**2 / 4 / 8 が要点。** 2 はバージョン 4 で実際に落とした穴、
4 は「29 文字」の罠、8 は設計方針そのものの検証。

## 9. 引き継ぎメモ（同じ失敗を繰り返さないために）

### 前提を疑うこと

- **仕様書に書いてある制約が、今の状況で効いているか確かめること。**
  このファイルの初版には「基板の書き込み直しは不要」「`PROTOCOL_VERSION` は 3 のまま」と
  書いてあったが、それは**公開済みの利用者がいる前提**の制約だった。
  まだ push も公開もしていない段階でこれを持ち込むと、存在しないコストで設計が歪む。
  実際、この制約を守ろうとして囲みブロックを避ける案を検討しかけた

### ビルドについて

- **ビルドは指示されたときだけ実行すること。** 勝手に走らせると、利用者が検証のために
  起動している `Scratch UIAPduino.exe` とぶつかり、`app.asar` のロックで失敗する
- ビルド前に `win-ia32-unpacked` を削除し、削除できたことを確認してから進めること
- **`.ino` を変えたら arduino-cli でコンパイルして確認すること。**
  利用者に「確認してください」と言わない。手順はグローバルメモリの
  `arduino_cli_build.md` にある

### ライブラリの中を読むこと

- **`Keyboard.write()` から `press()` / `release()` へ切り替えるとき、
  同じ引数で同じ結果になると思ってはいけない。**
  `press()` は修飾キーのビットを持つ文字（大文字と記号）でキーを押さない。
  実機で「`Hello` が `ello` になる」まで気づかなかった。
  **ライブラリの関数を差し替えたら、引数の全域について読み合わせること。**
  この 1 件で `PROTOCOL_VERSION` を 4 → 5 と 2 回上げ、2 回焼き直させた
- **`keyTap()` の出す HID レポート列は、机上で再現して確かめられる。**
  `Keyboard.cpp` の `press` / `release` / `_toHID` と `keyTap` を JS に写し、
  出たレポートを US 配列で読み戻せば「何が打たれるか」が分かる。
  **写したモデルが正しいかは、既知の不具合を再現できるかで確かめる**
  （旧 `keyTap` で `Hello` → `ello` が出れば、モデルは実機と合っている）

### 検証について

- **ブロック定義は、本物の `Runtime` に `_registerExtensionPrimitives()` で登録させて
  確認できる。** `getInfo()` を眺めるだけでは scratch-blocks 用 JSON の生成漏れに
  気づけない。**囲みブロックの `SUBSTACK` は `args1` 側に生成される**（`args0` ではない）
- **`runtime._primitives` を見ても意味がない。** ExtensionManager を通さずに
  `getInfo()` を直に渡すと `func` が文字列のままなので、実機確認済みのブロックも含めて
  全部 `undefined` になる。見るべきは「opcode に対応する実装メソッドがあるか」の方
- **`processor.request` を差し替えれば、デバイス無しでコマンド列を検証できる。**
  囲みブロックは `{stackFrame: {}, startBranch: () => {}}` を渡せば動かせる。
  キーボードのブロックはこの方法で 103 項目を確認した
- **`.ino` を正規表現で検査するときは CRLF に注意すること。**
  `/\/\/.*$/` は `.` が `\r` に一致しないため、`//` コメントを 1 つも落とせない。
  `[^\r\n]*` を使う。これで一度、誤検知に振り回された
- **実機の検証は、実際の使い方で行うこと。**（上記 8. を参照）

### やってはいけないこと

- **PowerShell で `user32` を叩く実装を作らないこと。** Avast が
  `IDP.HELU.PSE85`（コマンドライン検出）でブロックする。詳細は README
- **仮想キーを端から端まで走査しないこと。** 日本語 IME の環境では VK `0xF4` が
  常に「押されている」と報告される

### 既存の制約

- eslint は既存コードの時点で通っていない（`no-console` と、`'ja-Hira'` を含む
  メッセージ表の `quote-props`、`uiapduinoProcessor.js` の `prefer-template` /
  `valid-jsdoc`）。**新種の違反を増やさなければ十分**
- `Scratch-UIAPduino-*-sketch.zip` は**どのビルドスクリプトも生成していない。**
  手作業のものが残るため、`.ino` を変えたら取り残される

## 修正履歴

### 2026-08-07 — 大文字と記号が打てない不具合を修正（プロトコル 5）

実機で `Hello` とタイプすると `ello` になり、大文字が出ないという報告を受けた。

原因は `Keyboard.press()` の早期 return。バージョン 4 で `write()` から
`press()` へ切り替えたときに、**大文字と記号では挙動が違う**ことを見落としていた。
詳細は「[⚠ ただし `press()` に大文字を渡してもいけない](#-ただし-press-に大文字を渡してもいけない)」。

| 項目 | バージョン 4 | バージョン 5 |
|---|---|---|
| `キーボードで [Hello] と打つ` | `ello`（**大文字が消える**） | `Hello` |
| 記号（`!` `@` `?` など） | 打たれない | 打たれる |
| `Shift` を押しながら `[Hello]` | `ello` | **`hELLO`**（大文字小文字が反転） |
| 実装 | `Keyboard.press(k)` を直接 | `needsShift()` で分解し、Shift は自分で押す |
| Flash | 9804 (59%) | 10012 (61%) |

「押しっぱなしの Shift は大文字小文字を反転させる」は、このとき決めた仕様。

### 2026-08-07 — 実装に合わせて全面的に書き直し

初版（マウス完了時点で「これから作るもの」として書いたもの）から変わった点。

| 項目 | 初版 | 実装 |
|---|---|---|
| 修飾キーのブロック | `キーボードの [Ctrl▼] を押しながら [c] キーを押す`（1 コマンド） | `キーボードの [Ctrl▼] を押しながら〔 〕`（**囲みブロック**） |
| 囲みブロック | 「キーボードには用意しない」と明記 | **用意した。** マウスと同じイメージにしたいという判断 |
| `KEY_SHORTCUT`（`0x35`） | 使う。修飾ビット + キーコード | **削除。** キーボードに「ショートカットキー」は存在しない |
| `KEY_PRESS` / `KEY_RELEASE` | 露出しない。`PANIC` と将来の拡張のため | 露出しないのは同じだが、**囲みブロックが使う** |
| `PROTOCOL_VERSION` | 3 のまま。`.ino` は触らない | **4 に上げた。`.ino` も変えた** |
| 基板の書き込み直し | 不要 | **必要** |
| `Keyboard.write()` の待ち | press → 10ms → release → 50ms | **press → 20ms → release → 20ms**（実測。初版の記述は誤り） |
| `KEY_TEXT` / `KEY_WRITE` の実装 | `Keyboard.print()` / `Keyboard.write()` | **`keyTap()`**（修飾キーを壊さないため） |
| 修飾キーの値 | 修飾ビット `0x01`/`0x02`/`0x04`/`0x08` | **キーコード `0x80`〜`0x83`**（`KEY_PRESS` に渡すため） |

- `KEY_SHORTCUT` を消した理由 … 「[⚠ 「ショートカット」という概念は持たない](#-ショートカットという概念は持たない)」
